# <font size='5'>业务逻辑漏洞学习笔记</font>

## <font size='5'>一、核心概念与本质</font>

业务逻辑漏洞是指应用程序在实现业务功能时，其代码逻辑本身没有语法错误，但由于**设计缺陷或对业务规则的理解不完整**，导致攻击者能够以非预期的方式使用合法功能，从而达成对业务不利的结果。

它与 SQL 注入、XSS 等传统漏洞的根本区别在于：**传统漏洞利用的是代码实现的缺陷，而业务逻辑漏洞利用的是“代码正确、但规则错误”的灰色地带**。代码完全按照开发者编写的方式运行，但它执行出来的结果，并不是业务真正想要的结果。

OWASP 将其归类于 CWE-840（Business Logic Errors），并在 2021 年将其提升为独立类别 **A04:2021 – Insecure Design**。这类漏洞通常**无法被自动化扫描器发现**，因为扫描器不知道你的业务规则是什么，只知道常见的攻击特征。

## <font size='5'>二、常见类型与典型案例</font>

### <font size='5'>2.1 流程绕过与步骤跳跃</font>

多步骤业务流程是逻辑漏洞的重灾区。开发者常常假设用户会按 1→2→3 的顺序操作，但攻击者可以直接跳到第 3 步。

**典型案例**：某电商结算流程为“购物车→支付→确认订单”。如果“确认订单”接口只验证了用户会话有效，却没有验证支付是否已完成，攻击者可以直接调用确认接口，绕过支付拿到商品。

**变体**：MacWorld Expo 2007 的 VIP 通行证漏洞。网页源码中隐藏了 MD5 加密的折扣码列表，且校验在客户端 JavaScript 完成。攻击者发现密钥空间很小，直接暴力破解所有 MD5 码，免费获取了价值 1695 美元的 Platinum Pass。

### <font size='5'>2.2 参数篡改与价格操纵</font>

当应用程序信任客户端提交的关键业务参数（价格、数量、折扣、角色）而不在服务端重新校验时，就产生了操纵空间。

**常见手法**：

- **价格篡改**：将 `price=100.00` 改为 `price=0.01` 后提交订单。
- **数量负数**：将 `quantity=1` 改为 `quantity=-1`，使总价变成负数，实现“购物反赚钱”。
- **运费篡改**：商品价格被保护了，但运费字段未做校验，改为负数后抵扣商品金额。

### <font size='5'>2.3 竞争条件</font>

当“读取-判断-写入”操作不是原子性的时候，多个并发请求可能同时通过校验。这是金融和库存场景中最危险的逻辑漏洞类型之一。

**典型场景**：账户余额 100 元，攻击者同时发送 10 个取款 100 元的请求。每个请求单独看都是合法的（检查时余额充足），但并发执行后账户被透支。

**真实案例**：Coinbase Advanced Trade 平台曾存在竞争条件，允许账户卖出实际上并不持有的加密货币，Coinbase 为此支付了 25 万美元的漏洞赏金。Starbucks 的礼品卡转账接口也曾被 Egor Homakov 用并发请求演示过余额倍增。

**防御核心**：使用数据库层面的原子操作，如 `UPDATE balance SET amount = amount - 100 WHERE amount >= 100`，检查受影响行数，而非先 SELECT 再 UPDATE。

### <font size='5'>2.4 权限与身份逻辑缺陷</font>

**平行越权（IDOR/BOLA）**：将 URL 或请求体中的资源 ID（如 `order_id=1001`）改为其他值，直接访问他人的订单、地址或资料。First American Financial 曾因此暴露了 8.85 亿份保险文件，仅仅因为文档 ID 是顺序可遍历的。

**权限提升**：角色信息存储在 Cookie 或客户端本地存储中，攻击者将 `role=user` 改为 `role=admin`，服务端未独立验证就授予了管理员权限。

### <font size='5'>2.5 一次性功能滥用</font>

设计为“一次性”的功能被重复执行。

**典型场景**：

- 优惠券本应单次使用，但系统只标记了“已使用”而未在后续请求中校验，同一码可无限次使用。
- 免费试用期结束后，用同一设备/支付方式重新注册继续白嫖。
- **自我推荐**：用 A 账户生成推荐链接，用 B 账户注册，再让 B 推荐 A，循环套取推荐奖励。

## <font size='5'>三、检测与测试方法论</font>

业务逻辑漏洞的检测核心是**人工分析 + 逆向思维**，自动化工具在此几乎无效。

### <font size='5'>3.1 测试前的准备</font>

**理解业务规则**：获取或创建业务流程文档，明确以下信息：业务规则是什么、规则在哪里被强制执行、哪些数据从客户端传到服务端、每个字段的业务含义是什么。

**画出流程图**：将关键业务流程（注册、登录、下单、支付、退款）画成状态图，标注每一步的前置条件和后置状态。攻击点往往在**步骤之间的状态转换**上。

### <font size='5'>3.2 核心测试手法</font>

| 测试方向           | 具体操作                                                  | 预期安全表现                       |
| ------------------ | --------------------------------------------------------- | ---------------------------------- |
| **步骤跳过**       | 直接请求第 3 步的接口，不完成第 2 步                      | 返回 403 或重定向到缺失的步骤      |
| **步骤乱序**       | 在完成步骤 1 之前提交步骤 2 的数据                        | 服务器拒绝使用不完整状态           |
| **参数边界**       | 对数量/价格/时长提交负数、零、超大值、小数、Unicode 数字  | 400 错误，拒绝非法值               |
| **单位混淆**       | 提交不同货币单位或计量单位（如 IDR 混 USD）               | 服务端按用户区域或产品定义重新计算 |
| **隐藏字段篡改**   | 修改表单中 hidden 字段的布尔值或数值（如 `hasPaid`）      | 服务端从可信来源重新计算           |
| **并发测试**       | 用多线程工具同时发送 10-50 个相同请求（领取优惠券、提现） | 只有一个成功，其余被拒绝           |
| **一次性功能复用** | 重复调用“仅限一次”的接口（优惠码、试用、奖励）            | 第二次调用返回错误                 |
| **双账户交叉**     | 用账户 A 的会话访问账户 B 的资源 ID                       | 返回 403 或 404                    |

### <font size='5'>3.3 推荐工具</font>

由于逻辑漏洞依赖人工判断，工具主要是辅助观察和修改请求：

- **Burp Suite**：拦截、修改请求与响应，尤其是 `Do intercept → Response to this request` 用于观察服务端返回的状态码或隐藏数据。
- **浏览器开发者工具**：查看隐藏字段、本地存储、JavaScript 中的逻辑判断。
- **并发工具**：Burp 的 Turbo Intruder、自定义 Python 脚本或 `xargs -P` 用于竞争条件测试。

## <font size='5'>四、修复与防御原则</font>

### <font size='5'>4.1 核心原则：服务端信任最小化</font>

**绝不信任客户端提交的任何业务关键参数**。价格、折扣、角色、状态标志、数量都必须由服务端根据权威数据源重新计算或校验。客户端校验只用于改善用户体验，不能作为安全边界。

### <font size='5'>4.2 原子性与并发安全</font>

任何涉及“读取-判断-写入”的操作都必须使用数据库层面的原子操作。使用条件更新（`UPDATE ... WHERE condition`）并检查受影响行数，或使用 `SELECT ... FOR UPDATE` 行锁，或对关键操作使用唯一约束让数据库拒绝重复。

### <font size='5'>4.3 状态机与工作流显式化</font>

将业务流程建模为显式状态机。每一步在执行前必须验证前置状态是否已完成。不要依赖 UI 的导航顺序来隐含地保证流程正确。

### <font size='5'>4.4 一次性操作的幂等性设计</font>

对于发放价值的操作（优惠券、积分、试用），使用**幂等键（Idempotency Key）**。客户端重试时携带相同幂等键，服务端识别后返回缓存结果而不是重复执行。

### <font size='5'>4.5 针对滥用友好型功能的专项控制</font>

注册奖励、推荐、优惠券、密码重置等天生容易被滥用的功能，需要**独立于常规认证的额外控制**：

- 按功能维度而非全局维度做速率限制。
- 使用设备指纹、支付方式指纹、手机验证等身份信号，而非仅依赖邮箱。
- 对发放价值的操作记录详细审计日志（触发者、目标、IP、时间戳）。

### <font size='5'>4.6 防御性监控</font>

即使预防措施到位，也应部署异常检测来发现逻辑滥用行为：短时间内大量注册、同一支付方式关联多个账户、优惠券核销率异常等。



## <font size='5'>五、学习与实战建议</font>

业务逻辑漏洞挖掘能力的提升，核心不在于工具熟练度，而在于**对业务的理解深度和“如果我是攻击者”的思维切换**。

**入门阶段**：从自己常用的电商、社交、SaaS 产品入手，观察它们的业务流程（下单、退款、会员升级），尝试在脑海中画出状态图，然后问自己：如果跳过某一步会怎样？如果修改某个参数会怎样？

**进阶阶段**：研究公开的漏洞赏金报告中的逻辑漏洞案例。Coinbase 的竞争条件、First American 的 IDOR、Stripe 的优惠码复用都是经典教材。重点关注攻击者“发现了什么规则没有被强制执行”。

**实战阶段**：在授权测试中，拿到一个功能后先不要急着测注入和 XSS，先完整走一遍正常流程，记录每一个请求和每一个状态变化，然后系统性地偏离正常路径。参考 OWASP WSTG 的 Business Logic Testing 章节的测试用例清单作为起点，但最终要靠自己对当前业务的理解来设计“业务规则违例测试用例”。
